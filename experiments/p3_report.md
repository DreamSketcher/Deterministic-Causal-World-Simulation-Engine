# P3 — профиль дорогих операций (шаг 7)

Измерено на этом железе (2 vCPU-песочница, Python 3.12, CPython-хэш sha256) скриптом
`experiments/p3_profiling.py`, два прогона: базовый (текущий код) и `--optimize`
(инкрементальный хэш архива, тот же канон). Сырые числа:
`p3_profile_data_base.json`, `p3_profile_data_opt.json`.

**Главный контроль: профилирование не тронуло семантику.** Отпечатки жизней
(`bio_fingerprint`), финальный `state.hash()`, число строк архива (66 738) —
**идентичны между прогонами** (`IDENTITY identical: True`). Ни один хэш не изменился.

## Что измерялось и чем

| Режим | Мир | Тик | Операция |
|---|---|---|---|
| M1 | 4×50, player_life, persist / memory | 300 | стоимость тика (step+resolve+SQLite) |
| M2 | тот же архив, переоткрытый (38 324 строки) | — | `journal.hash()` cold / cached / append+hash |
| M3 | 2×30, длинный журнал | 5 000 | play + полный реплей + декомпозиция этапов + RAM (tracemalloc) |
| M4/M5 | 4×50, seed 21, natural chain | — | 8 жизней × ≤150 решений: takeover/bio/play по каждой жизни |
| M6 | аналитика по M4 | — | фит a·T+b, цена 50-жизненного цикла, break-even снапшота |

## M3 — длинный журнал (5 000 тиков, 64 233 строки)

play 15.6 s (320 тик/с). Полный реплей: steps 11.2 s + rehash-при-reopen 3.1 s +
чтение стрима из view 1.6 s ≈ **16 s**. tracemalloc peak реплея **218 MB** (для 2×30;
RAM растёт линейно с числом записей — 4×50 ≈ ×10). Tracing сам по себе ×3–4 к шагам.

*Честная сноска:* флаг `replay_hash_eq_archive: False` в M3 — артефакт харнесса
(реплей без игрока прицепил канал с idle-фолбэком, а «игрок причинен» — расхождение
по теории), идентичен в обоих прогонах; настоящий путь `replay_head` (строгая
сверка, refuse при расхождении) — покрыт Check A в тестовом наборе.

## M6 — когда линейный реплей становится проблемой

Фит по takeover: `T = 0.0105 s × head_ticks + 1.09 s` (base; opt: `+0.80` — хэш-часть
исчезает, шаговая остаётся). Стоимость реплея почти не зависит от способа хэширования:
это повторный `step()`, 10.5 ms/тик для 4×50.

* takeover на T=1 000 ≈ 11.6 s, T=2 000 ≈ 22 s, T=20 000 ≈ 212 s (3.5 мин на одну жизнь).
* **50 жизней × 400 тиков: суммарно ≈ 5 429 s (base) / 5 608 s (opt) реплеев** —
  **это экстраполяция по фиту, не прогон**: естественный мир вымирает раньше
  (seed 7: no_heir; seed 21: 8 жизней за лимит; 50-жизненного цикла при нынешних
  правилах не существует — конец света калибровать не наша задача).
* Break-even снапшота: реплей = 74 % цены живой игры за тик; снапшот окупается,
  когда хвост реплея+сверка > повторного шага всей истории, т.е. T ≳ несколько
  тысяч тиков **на takeover**. При текущем времени жизни мира (вымирание ≈ T 900–1
  000, takeover ≤ 10 s) — не оправдан.

## Вердикт

1. **Настоящая, измеренная проблема — не реплей takeover, а `hash()` на каждое
   решение после переоткрытия архива**: O(N) на кадр (1.1–1.9 s при 38–100k строк),
   квадратичный рост по жизни; жрёт 95 % времени длинной сессии (1 200 s из 1 260).
2. Инкрементальный хэш (тот же канон, формат не трогать) убирает её полностью
   (**10–168× на play, ×20 на цепь**) при нулевом изменении формата и доказанной
   идентичности всех хэшей. Кандидат на минимальный эксперимент — это она.
3. Снапшот + хвост — отложить: оправдан только при глубинах T ≥ 5–10k на takeover,
   которых игра при текущих правилах не видит; решение привязать к исходу P2
   (калибровка «бессмертных» режимов). Данные для break-even в M6.
4. RAM: память журнала линейна (64k строк ≈ 218 MB реплея, 900-тиковая цепь ≈ 697 MB
   процесса) — при бессмертных мирах станет вторым ограничителем после CPU.
